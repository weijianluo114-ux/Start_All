# BUG-002 · 部分程序「能打开、关不掉」

- **状态**：已修复
- **严重度**：严重（核心功能失效，且旧版不给失败原因）
- **发现日期**：2026-10-19
- **报告人**：用户（`dsh-tauri-app.exe`、`WorkBuddy.exe` 两个条目）
- **影响版本**：v1.3.0 – v1.4.0
- **修复版本**：v1.4.1
- **关联**：REQ-002、FEAT-003、T-004

## 现象

- 「🚀 一键启动」能正常打开这两个程序；
- 「⏹ 关闭所有程序」确认后，程序仍在运行，界面只显示"关闭失败"，没有任何原因说明；
- 其他程序（如 ping 探针、普通 exe）关闭正常。

## 排查过程

按"权限 → 路径 → 进程 → 代码"的顺序逐层排除，全部为只读操作。

### 1. 权限不是原因

用 `OpenProcess(PROCESS_TERMINATE)` 直接探测目标进程，并读取其 Token 提权状态：

```
dsh-tauri-app.exe   pid=21380  TERMINATE权限=True  提权=False
WorkBuddy.exe(main) pid=20976  TERMINATE权限=True  提权=False
WorkBuddy.exe(child)pid=19140  TERMINATE权限=True  提权=False
对照 explorer.exe   pid=30968  TERMINATE权限=True
```

当前进程未提权，但目标同样未提权，且句柄可获取 —— 排除 UAC / 权限不足。

### 2. 条目形式与镜像名都正确

两个条目在配置里是快捷方式：

```
C:\Users\Public\Desktop\WorkBuddy.lnk      → ...\WorkBuddy\WorkBuddy.exe
C:\Users\28792\Desktop\DSH Desktop.lnk     → ...\DSH Desktop\dsh-tauri-app.exe
```

用真实配置跑只读判定，两者都被识别为"运行中"，镜像名（`WorkBuddy.exe` / `dsh-tauri-app.exe`）与运行进程完全一致。路径解析没有问题。

### 3. 进程结构

`WorkBuddy.exe` 共 9 个进程（Electron 多进程），`dsh-tauri-app.exe` 1 个（Tauri）。两者都是典型的**单实例桌面应用**。

### 4. 代码审查发现两处缺陷

```python
if launched is not None:
    ...
    if pid: self._taskkill(['/f','/t','/pid', str(pid)])
elif image:                     # ← 缺陷 1
    self._taskkill(['/f','/t','/im', image])

# 缺陷 2：只判断"有 PID"，不判断 PID 是否还活着
if pid or launched[3]:
    running.append((path, image))
```

## 根因

**单实例应用导致启动记录里的 PID 在关闭时早已失效，而旧实现让"按镜像名关闭"成了互斥分支，永远走不到。**

完整链路：

1. WorkBuddy / DSH 本来就在运行（用户日常开着）；
2. 用户点「一键启动」，`subprocess.Popen` 启动了一个新进程，并被记录进 `launched_items`；
3. 单实例机制生效：新进程把启动请求转交给已有实例，**自己立即退出**；
4. 用户点「关闭所有程序」时：
   - `_find_launched` 命中这条记录 → 只执行 `taskkill /f /t /pid <已退出的PID>` → 返回 `rc=128, not found`；
   - 由于是 `elif`，`/im WorkBuddy.exe` 这一步被跳过；
   - 结果：什么都没关掉。
5. 同时判定用 `if pid` 而非"PID 存活"，所以确认框照常列出这两个程序，用户看到的是"确认了却关不掉"。

> 说明：没有直接对用户正在运行的两个应用执行终止来"现场复现"（其中 WorkBuddy 正是当前工作环境）。
> 上述结论由两条可验证事实推出：镜像名与真实进程一致、旧代码在存在启动记录时不执行镜像名关闭；
> 并在 T-004 中用"进程在跑 + 记录 PID 不存在"的等价场景做了对照验证。

## 修复（v1.4.1）

| # | 改动 | 目的 |
|---|---|---|
| 1 | 镜像名关闭**无条件执行**（PID 之后一定跑 `/im`） | 消除 `elif` 互斥，PID 失效也能关掉 |
| 2 | 判定改为 `_pid_info()`：PID 存活**且**镜像匹配才算本次启动的进程 | "有记录"≠"在运行"；同时防 PID 复用误杀 |
| 3 | 关闭后轮询复查（最长 3 秒） | 避免多进程应用退出滞后造成的"假失败" |
| 4 | 识别「拒绝访问」→ 可选用管理员权限重试（一次 UAC） | 覆盖真正以管理员运行的程序 |
| 5 | 全链路日志：`taskkill` 命令、退出码、原始输出、判定与失败原因 | 以后无需猜测 |
| 6 | 结果框附失败原因与日志路径，新增「🗒 日志」按钮 | 用户可直接查看 |
| 7 | 日志按 1 MB 轮转保留 3 份；未捕获异常 / 线程异常入日志 | GUI 下崩溃可追溯 |

日志位置：`%LOCALAPPDATA%\MultiLauncher\logs\launcher.log`

## 回归验证（T-004）

用 `ping.exe` 副本 `lf_single_probe.exe` 模拟"程序早已在运行"，再注入一条 **PID 999999（不存在）** 的启动记录：

| 阶段 | 结果 |
|---|---|
| 修复前逻辑 | `/pid 999999` 返回 128 后跳过 `/im`，进程存活（即用户看到的现象） |
| 修复后 | `/pid` 跳过（已确认 PID 失效）→ `/im` 返回 0，进程终止 |
| 日志 | 含「记录 PID 999999 已失效」「taskkill /f /t /im lf_single_probe.exe → rc=0」 |
| 结果框 | 「已关闭 1 个程序」 |

## 残留限制

- 镜像名关闭仍是 `/im` 语义：列表里放一个同名程序，会关掉系统中所有同名实例。
- 若程序有守护进程会自动重启，结果会显示"进程仍在运行（可能被后台服务重启）"，日志中可看到 `rc=0` 但复查仍在。
- PID 复用防护只覆盖"按 PID 关闭"这一步；`extra_pids`（批处理拉起的子进程）未做镜像核对。

## 经验

1. **不要用 `elif` 把主路径与兜底路径做成互斥**——兜底就该无条件执行。
2. **退出码与原始输出必须落盘**：`taskkill` 的 `rc=128` 与"拒绝访问"是两类完全不同的问题，旧版一律吞掉，导致无从排查。
3. "存在启动记录"不等于"进程还在"，判断运行状态要基于存活探测。
4. 单实例应用（Electron / Tauri / 各类桌面客户端）在"重复启动"场景下，记录的 PID 天然不可靠，必须保留镜像名兜底。
