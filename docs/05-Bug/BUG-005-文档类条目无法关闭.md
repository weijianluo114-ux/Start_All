# BUG-005 · 文档类条目能打开但关不掉

- **状态**：已修复（v1.9.1）
- **发现**：2026-10-20
- **影响版本**：v1.0.0 ~ v1.9.0
- **关联**：FEAT-005、T-011

## 现象

把 `deformable_attention_整体框图.drawio` 拖进列表，点左半圆能正常用 draw.io 打开；
点右半圆却提示"无需关闭"，日志里这一条被标记为：

```
程序跳过 1 项 [('deformable_attention_整体框图.drawio', '脚本类且非本次启动，无法判定')]
```

即启动器认为"没有程序在运行"，实际上 drawio 就开着。

## 复现

1. 列表加入任意 `.drawio` / `.md` / `.docx` 文件（**不是** `.exe` / `.lnk`）；
2. 点左半圆启动，文件被关联程序打开；
3. 点右半圆 → 提示"无需关闭"。

对照：`.lnk` 条目（如 `WorkBuddy.lnk`）能正常关闭，`*.exe` 也正常。

## 根因

两层信息同时缺失，缺一不可。

### 根因一：启动侧拿不到 PID

`launch_program()` 对非 exe 走 `WScript.Shell.Run(文件路径, 1, False)`。
实测（本机 drawio + `.txt`）该调用**返回 0**——操作成功但没有进程 PID：

```python
pid = shell.Run(TARGET, 1, False)   # → 0
if pid: ...                          # 0 为假，于是走 os.startfile 并 return None
```

于是 `_launch_worker` 只打了日志、**没有把这一项写入 `launched_items`**：

```
16:01:56 [INFO] 启动完成但未取得 PID：…drawio（由系统关联程序打开）
```

### 根因二：关闭侧没有镜像名

`_close_targets()` 只对 `.exe` / `.com` 生成镜像名，其余（含 `.drawio`）一律 `None`：

```python
if ext in ('.exe', '.com'):
    targets.append((p, os.path.basename(resolved)))
else:
    targets.append((p, None))        # .drawio 也落到这里
```

判定时 `image is None` → 直接 `skipped('脚本类且非本次启动，无法判定')`。

### 为什么 `.lnk` 不受影响

`resolve_lnk()` 会把 `.lnk` 解析成真实的 exe 路径，镜像名有值，所以能判定。
文档类文件没有"解析成 exe"这一步，必须借助**文件关联**。

## 修复

### 1. 启动侧：改用 ShellExecuteEx

`open_via_shell()` 用 `ShellExecuteExW` + `SEE_MASK_NOCLOSEPROCESS` 打开文件，
通过返回的 `hProcess` 取 `GetProcessId`。实测对 drawio 有效：

| 调用 | 结果 |
|---|---|
| `WScript.Shell.Run(…drawio, 1, False)` | 返回 `0` |
| `ShellExecuteExW` → `hProcess` → `GetProcessId` | 返回 `21316`，1 秒内命令行命中 `draw.io.exe "…drawio"` |

### 2. 关闭侧：新增两层判据

| 优先级 | 判据 | 说明 |
|---|---|---|
| 1 | **命令行含文件路径** | `find_pids_by_commandline()`：WMI 查 `Win32_Process.CommandLine`，命中即"就是这个进程打开了该文件"——最精确 |
| 2 | 启动记录里的 PID | 原有逻辑 |
| 3 | **文件关联的宿主程序名** | `assoc_executable()`：`AssocQueryString(ASSOCSTR_EXECUTABLE)`，`.drawio` → `draw.io.exe` |
| 4 | 登记的伴生进程 | 原有逻辑（Steam 中转脚本等） |

第 1 层全部关闭成功时**不再**走第 3 层，否则"关一个文件"会退化成"关掉该程序所有窗口"。

### 3. 过滤系统兜底宿主

`AssocQueryString` 对没有默认程序的扩展名会返回 `OpenWith.exe`（"打开方式"对话框的宿主）。
若不处理，任何未知扩展名都会被当成"有关联程序"，甚至误判为"已运行"。
因此把 `OpenWith.exe` / `ApplicationFrameHost.exe` / `dllhost.exe` / `explorer.exe` /
`LaunchWinApp.exe` 列入黑名单，命中即返回空。

### 4. 统计口径修正

`_kill_target()` 精确关闭成功后返回 `precise_closed=True`，统计时直接计为成功。
否则复核会拿关联程序名去比对：`.py` 的关联程序是 `Code.exe`，用户的 VS Code 当然还在运行，
于是把"已经关掉"的条目误报成"进程仍在运行（可能被后台服务重启）"。

## 已知边界

1. **UWP / 商店应用拿不到进程句柄**：本机 `.txt` 关联到商店版记事本，
   `ShellExecuteEx` 返回成功但 `hProcess` 为空，此时退回"命令行 / 关联程序名"判定。
   UWP 应用的命令行通常也不含文件路径，最终只能按镜像名（如 `Notepad.exe`）关闭。
2. **单实例应用把请求转交给已有实例**：新进程随即退出，主进程命令行里不会有新文件，
   第 1 层匹配不到 → 回落到第 3 层按镜像名关闭，会连带关闭该程序的其它窗口。
   确认框里会标注"将关闭 xxx 的全部实例"。
3. **命令行匹配依赖 WMI**（`Win32_Process.CommandLine`）：枚举约 400ms，只在关闭时执行一次；
   WMI 不可用时自动跳过该层，不影响其它判据。
